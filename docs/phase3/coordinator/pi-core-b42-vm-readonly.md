# B42: can this host present the B41 disk as read-only NVMe?

**The exact disk was accepted by Apple's host-side NVMe descriptor; guest-visible read-only status remains unproved.** The installed Apple SDK identifies 512 bytes as the raw attachment block size. Neither vendor interface reviewed establishes that this Ubuntu kernel will observe both **512-byte logical sectors** and **a read-only namespace advertised to the Linux block layer**. This is a missing guarantee, not an observed boot failure or proof that either backend is incapable. The B41 gate stays unchanged.

## What was checked

Inspected host package metadata, public SDK declarations and upstream documentation/source, not any existing VM's files or state. The host reported arm64 macOS 26.6.2 (25G83). The installed Fusion app bundle reported 26.0.0, build 25388279. The public Apple Virtualization headers inspected were from Command Line Tools' MacOSX26.5 SDK. The local Homebrew package directories showed Lima 2.1.4 and Colima 0.10.3. No `qemu-system-aarch64` was present on the selected PATH or in the standard Homebrew QEMU Cellar; that is not an exhaustive search for third-party installations.

The coordinator's [host descriptor probe](../../../packaging/pi-core/immutable-host-b42/vz-attachment.m) opened the exact retained B41 raw path with `readOnly:YES`, verified its URL and `isReadOnly`, and observed that the NVMe controller configuration retained that same attachment object. Focused stage `pi-core-nvme-attachment-offline` passed under fingerprint `eb88cdc646c1e35b9da01db02889c6629f0ba9cba5e395148c43f80e08e89639`. It instantiated neither a VM configuration nor a VM and did not start a guest, change a disk, or call a guest ioctl. The SDK header `VZDiskImageStorageDeviceAttachment.h` documents a raw image file length divisible by its 512-byte block size; this is positive host-side geometry evidence, distinct from a measurement of the emulated namespace's LBA format.

## Why a host write refusal is not enough

B41's [initramfs guard](../../../packaging/pi-core/immutable-host-b41/boot-init.c) checks `BLKROGET == 1` on **both** the whole NVMe disk and partition 2, `BLKSSZGET == 512` on the whole disk, the exact partition length, sealed root bytes and zero sector padding. Canonical's [matching 7.0.0-14.14 source](https://git.launchpad.net/~ubuntu-kernel/ubuntu/+source/linux/+git/resolute/tree/debian.master/changelog?id=4c11409bcfb0d6460cda473513e37449f1f59dbb) answers the [two ioctls](https://git.launchpad.net/~ubuntu-kernel/ubuntu/+source/linux/+git/resolute/tree/block/ioctl.c?id=4c11409bcfb0d6460cda473513e37449f1f59dbb#n688) from the block device's read-only state and logical block size, not a trial write. The [NVMe Identify code](https://git.launchpad.net/~ubuntu-kernel/ubuntu/+source/linux/+git/resolute/tree/drivers/nvme/host/core.c?id=4c11409bcfb0d6460cda473513e37449f1f59dbb#n1636) reads the namespace's read-only attribute, and [propagates the read-only state to the block disk](https://git.launchpad.net/~ubuntu-kernel/ubuntu/+source/linux/+git/resolute/tree/drivers/nvme/host/core.c?id=4c11409bcfb0d6460cda473513e37449f1f59dbb#n2434). This is source-level evidence, not an observation from the Ubuntu guest.

`chmod 0400` on the host, a filesystem mounted read-only, a copy-on-write layer, GPT's partition attribute, or forcing `BLKROSET` inside the guest does **not** demonstrate the approved whole-disk device property.

## Decision before execution

A candidate for a **separately authorized compatibility observation** is an owned, isolated Apple VZ generic VM with exactly one NVMe controller, one explicitly read-only attachment to a byte-verified copy of the B41 disk, and no network, host shares, existing disks or writable overlay over the candidate. This is not a recommendation to boot on this Mac. The [B42 trust decision](pi-core-firmware-trust-batch-42.md) documents the macOS 27 minimum for Apple's public enrollment/readback APIs; the inspected host is 26.6.2. First establish the trust path on the chosen backend and specify the runner, private firmware-variable store, bounded timeout, ownership and cleanup/readback. An ordinary firmware boot or a read-only copy alone does not close that trust gate.

If subsequently authorized, retain independent evidence of the guest's device identity and guard outcome, exact disk/partition geometry, absence of write authority and cleanup. Do not attempt writes to prove a negative, set a guest flag to obtain a pass, silently switch to VirtIO, retry on a different VM, or classify an unobserved refusal as success. If those device properties cannot be demonstrated, stop for an alternative backend or a reviewed successor architecture. Boot authorization would not authorize a provider call, a useful pilot or D5.
